# 三层协同：App 端、后端、视频来源

秒开靠三层减少关键路径上的工作：后端尽快交付可用地址，视频来源尽快交付可解码数据，App 提前准备并复用播放资源。高清画质与低延迟可以同时追求，关键是合理编码、分发和调度。

```mermaid
flowchart LR
    A[视频来源：原始高清素材] --> B[转码：画质与码率平衡]
    B --> C[封装：MP4 faststart 或 HLS]
    C --> D[点播存储与 CDN]
    E[后端：目录与最新权限] --> F[缓存命中并附带播放窗口]
    F --> G[App：直接消费有效地址]
    D --> H[媒体字节与清单]
    G --> H
    H --> I[预建资源与当前集优先解码]
    I --> J[真实首帧与邻集预热晋升]
```

## 一、App 端：先准备资源，再复用正确结果

| 技术点 | 当前项目的实现 | 解决的问题 |
|---|---|---|
| 启动预创建 | IO 打开共享缓存，主队列空闲时创建全局五个无媒体播放器 | 把对象初始化移出点击后的关键路径 |
| 五槽独立播放资源 | 每槽独立 Builder、播放线程、LoadControl 和预加载管理器；该槽内播放器与预加载器配套构建 | 避免五路共用同一个播放队列而相互阻塞 |
| 全 App 共享资源组 | 首页、详情等页面接管同一组五槽，逻辑会话独立，前台独占 | 防止跨页再创建一组，保持唯一发声者 |
| 当前集首帧优先 | 地址预取提前；邻集解码 prepare 等当前真实首帧后启动 | 避免邻集先抢走有限的解码资源 |
| 有界邻集预热 | 详情当前及前后两集保留输出；更远项可只预取数据 | 切集直接晋升已准备结果，控制资源消耗 |
| 三级结果复用 | URL 缓存/在途合并、媒体磁盘缓存、Player/MediaItem/输出身份复用 | 防止“数据热了，但落定后又重新请求和 prepare” |
| 带宽与任务调度 | 推测取址最多两路，当前明确目标优先，缓冲饥饿时预热让路 | 优先保障正在观看的视频 |
| 精确续播与 HTTP | 按真实位置续播，首帧前临时定位加速；特定提前关闭路径取消旧 HTTP Call | 处理长 GOP 前滚和未读响应关闭等待 |
| 生命周期与事件归属 | 暂停/后台/音频焦点门禁，拒绝旧会话和旧输出回调 | 速度与播放正确性共同保持 |

“独立播放池”在此具体指五槽各自的播放队列、缓冲控制和预加载器。全局仍是一组五个播放器，并非五个池各自再创建五个。CPU、硬件 decoder、带宽与磁盘缓存仍由设备共享。详细实现见 [播放器设计](04-player.md)。

## 二、后端：播放地址的获取路径尽量短

优先让一次目录请求返回最新权限、当前集以及有限邻集的可用地址。客户端拿到有效地址就直接消费，避免“目录 → 视频 ID → 再查地址 → 再查更多地址”的重复串行往返。

后端内部也要缩短：先批量查地址缓存，命中直接组装；短 URL 与完整 VOD 信息分开存；未命中有界并发获取并回写。不要把原来客户端的多次请求改成后端内部逐条等待。数据表、关联查询、聚合缓存一起为这一条关键路径服务。

目录和业务权限需要及时刷新；地址缓存只复用有效来源，不能替代权限验证。后端源码未在本包提供，具体数据库与缓存实现的证据范围见 [数据与缓存](03-data-and-cache.md)。接口与入口差异见 [接口设计](02-api.md)。

## 三、视频来源：让高清内容也能快速开始

- 普通 MP4 使用 **faststart**，把 moov 索引放到媒体数据前面，减少获取初始化信息时跳到文件尾的需要。它是封装优化，不会重新压缩画面。
- 用转码把分辨率、编码、码率、GOP 和终端兼容性一起考虑，目标是在可接受画质下减少需要传输和解码的负担。不能只追求更高压缩率而忽略解码支持。
- 使用阿里云、字节/火山引擎等点播服务的转码、存储和 CDN 能力，减少自己搭建媒体处理与分发链路的成本。供应商能力不表示本项目已经接入所有供应商。
- CDN 使用媒体加速域名，核对 Range、缓存命中和首字节等待；不要把业务接口服务器当媒体代理多转发一跳。

参数、命令、来源和验收见 [视频来源、faststart 与云点播](08-media-source.md)。

## 如何复制到另一个项目

先量出点击到真实首帧各阶段，再判断这三层哪里在等待。五槽是本项目实装方案，其他设备应据资源能力选择窗口；文档里的“预创建五个对象”与“预先解码五路视频”需要区分。当前实测、历史迭代对照分别列在 [性能测量](06-measurement.md)。
